# Three bugs I only found on real hardware

> 这三条问题在模拟器上、在单元测试里、在"看起来能跑"的 demo 里都不会出现。
> 它们各自代表一类东西：协议细节、硬件实现差异、客户端库的隐形上限。
> 记在这里，是因为每一条都花了远超预期的时间才定位到根因。

---

## 1. SPS 只有 7 字节，被当成脏数据丢掉了

### 现象

分段出来的 MP4 送去 ffmpeg 解析，报：

```
sps_id 0 out of range
non-existing PPS 0 referenced
```

日志里能看到：

```
[Warning] 跳过SPS：长度=7字节，太短（要求至少8字节）
cached_sps=无, cached_pps=有
```

只有 PPS 被缓存下来，没有 SPS。后续每个分段只补了 PPS，所以全部解码失败。

### 根因

两件事叠在一起：

1. **代码里硬编码了 `SPS 至少 8 字节` 的判定**。这个数字是拍脑袋的——不同编码器生成的 SPS 长度不一样，
   简单的流 SPS 可能只有 7–10 字节。7 字节在这里是完全合法的。
2. **H.264 流里可能有多个 SPS/PPS**，第一个往往不完整，需要取**最后一个（最新的）**。
   原实现遇到第一个就判断，判断错了就丢了。

### 解决

- 最小长度阈值从 8 降到 5（起始码 3–4 字节 + NAL 类型 1 字节 + 至少 1 字节数据）
- 遍历全部 NAL 单元，**保留最后一个** SPS/PPS；如果新的比已缓存的更长，就覆盖缓存
- 提取时严格按"从起始码到下一个起始码"截断，避免把下一个 NAL 的数据带进来

### 原记录

> **实时采集编码注意**：Android 端为每个关键帧前置完整 SPS/PPS（启用 `MediaFormat.KEY_PREPEND_HEADER_TO_SYNC_FRAMES`），
> 保证分段 MP4 独立可解码，避免因缺少 PPS 导致封装/播放失败。

## 2. 竖屏采集出现绿色/紫色条纹

### 现象

竖屏采集时，画面出现绿色/紫色的横向条纹。同一个 App 横屏正常。

### 根因

**编码器输入色彩格式不匹配。** 绝大多数 Android 硬件编码器吃 NV12（半平面，UV 交错），
但某些设备（实测 Pixel 6a）实际使用 `COLOR_FormatYUV420Planar`（I420，U/V 分离平面）。
代码一直按 NV12 喂数据 → UV 平面整体错位 → 颜色全乱。

这类问题最难的地方在于：**没有任何报错**，编码器照常输出，只是画面是错的。

### 解决

1. 从 `MediaCodec` 的 `outputFormat` 读取实际的输入色彩格式，不要假设
2. 如果是 Planar，送进编码器前把 NV12 转成 I420
3. 时间戳用 CameraX 的真实帧时间戳（`image.imageInfo.timestamp`），而不是按固定间隔累加
4. **预览方向和编码方向解耦**：预览用显示方向的 `targetRotation`，编码用「物理方向 + 摄像头映射」算出的
   `rotationForBackend`。两者混用会出现双重旋转或方向误判

关键点在 `H264Encoder.encode()`：按 `encoderColorFormat` 动态选择 NV12 或 I420。

### 额外收益

改用真实帧时间戳之后，视频的实际 FPS 反映真实捕获速率（可能是非整数），播放速度与现实时间对齐。

## 3. 60 秒分段 16.3 MB，客户端静默断连

### 现象

录制进行到某一刻，App 自己停了。服务端只看到一条 `capture_stopped`，没有明显异常。

### 根因

1920×1920 @ 4fps、2MB 码率下，单段 60 秒约 12.8 MB MP4；**Base64 编码后约 16.3 MB**，
超过 OkHttp WebSocket 客户端发送队列的 **16 MB 硬上限**。`send()` 返回 `false`，队列溢出后连接被放弃。

关键点：这个上限在**客户端**，和服务端的 `WEBSOCKET_MAX_SIZE_MB` 完全无关。
调服务端配置一点用没有。

### 解决

反推单段体积上限，让它满足 `Base64 后 < ~15.5 MB`（约等于 MP4 < ~11.6 MB）：

1. 缩短分段时长（60s → 30s）
2. 降低码率（实测 1MB 码率、60s 分段约 6.9 MB MP4，Base64 后 8.7 MB，稳定发送）
3. 降低分辨率或帧率

另外，Gemini 2.5 Flash 走 OpenRouter 时视频是 Base64 随请求体发送的，
单段建议控制在 15 MB 以内，否则会 `Payload Too Large`。

## 这三条放在一起看

它们的共同点是：**问题都不在业务逻辑里，而在你默认成立的那些前提里**。

- 「SPS 至少有 8 字节」——对协议实现的假设
- 「硬件编码器都吃 NV12」——对设备一致性的假设
- 「WebSocket 能发出去」——对客户端库的假设

这三条假设，在文档里都没写。只能靠真机、真网络、真分段去撞。
